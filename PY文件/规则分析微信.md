## 一、微信小包上传 -- 关键特征

### 联通 (36条记录, 24个小包段)
| 字段 | 值 |
|---|---|
| 固定文件大小 | **~5MB (实际5.35MB)** |
| 持续时长 | **0~2秒（典型1秒）** |
| 上行RLC速率 | 2行段平均21~22Mbps, 1行段平均43Mbps |
| dlRlc | 0.06~1.61Mbps（ACK流量，~0.72平均） |
| 总流量 | 3.9~5.35MB/段 |

小包上传分为两种形态：
1. **2行段**（14段）：两行ulRlc之和在40~43Mbps范围，持续时间约1秒，总流量≈5.35MB。
   - 第一行约15-35Mbps（初速爬坡），第二行约9-35Mbps
   - 两行平均约21.5Mbps × 2秒（实际上约1秒内完成发送）
2. **1行段**（10段）：单行ulRlc=42.9~43.0Mbps，约0秒内完成，总流量≈5.35MB。
   - 速率为43Mbps × 1秒 = 43Mbps，约是5.35MB

> **核心结论**：微信小包是固定5MB文件上传，速率≈43Mbps（近上限），所以1秒即可完成。部分场景因上行信号一般，出现2行（爬坡+稳定两段），平均速率减半到21.5Mbps。

### 电信 (47条记录, 28个小包段)
与联通几乎完全一致：
- 2行段：总流量5.35MB, 平均速率21.5Mbps
- 1行段：单行43Mbps, 总流量5.35MB
- 少数异常段(3行、部分低速率)：流量略减至4.1~4.5MB

**跨运营商一致性**：100%符合，5MB固定文件。

### 小包 vs 背景噪声
| 特征 | 微信小包上传 | 背景噪声(空闲态) |
|---|---|---|
| ulRlc | **>40Mbps(1行)或合计>40Mbps(2行)** | <0.1Mbps |
| 持续时间 | <2秒 | 连续数十秒 |
| dlRlc | 0.2~1.6Mbps(ACK) | <0.1Mbps |
| 流量累计 | ~5MB | <0.1MB |
| UM MAC Thrpt | 3100万bps平均 | <10万bps |

**区分规则**：小包在背景噪声中突兀出现1~2秒，ulRlc从<0.1飙升至>5Mbps(起始)再到35+Mbps。噪声段ulRlc始终<0.5Mbps。阈值：**ulRlc > 5Mbps 且持续1~2秒就是小包**。

## 三、微信大包 vs FTP上传（泰尔网测上传）的区分规则

### 关键对比
| 特征 | 微信大包上传 | FTP上传(联通) | FTP上传(电信) |
|---|---|---|---|
| 固定文件大小 | **215MB** | **149MB** | **107MB** |
| 持续时长 | 10~42s（典型24s） | **~17s** | **~17s** |
| 平均速率 | 40~158Mbps(典型68) | 66.4Mbps | 47.7Mbps |
| 上行MAC Thrpt | 6660万bps平均 | 7480万bps平均 | - |
| QCI分布 | 60% QCI6, 34% QCI6;5 | 94% QCI6;5 | - |
| 下行RLC | 0.07~2.21Mbps | 0.44~1.02Mbps | - |
| UL BSR | 非零均值5.5亿byte | 均2.6亿byte | - |

### 区分规则

**规则A：流量大小法（主规则）**
- `flow < 20MB` → 微信小包
- `20MB ≤ flow ≤ 80MB` → 无法判断（联通FTP有149MB，电信FTP有107MB，都不在此区间）
- `80MB < flow < 190MB` → **FTP上传**（因为微信大包最小206MB）
- `flow ≥ 190MB` → **微信大包上传**（因FTP上传联通149/电信107，均<190MB）

**规则B：流量+时长联合法（备用）**
- 微信大包：flow ≈ 215MB，时长与速率成反比
- FTP上传：flow在107~149MB范围，时长≈17秒固定
- 当流量在150~190MB区间时，看时长：<21秒为FTP上传，≥21秒为微信大包

**联通基准_FTP上传的QCI全为"6;5"或"5;6"**（多QCI承载），微信大包60%为纯QCI6、34%为6;5。但QCI区分度不够清晰，不建议作为唯一规则。

**当前脚本规则**（`5G用户级公共监控速率统计工具-V1.04.py`）：
```python
if flow < 20: return 'wx_s'               # 5MB→微信小包
if flow > 80:
    if dur < 21: return 'ftp_ul'          # 150MB/17s→FTP上传
    return 'wx_l'                         # 215MB/24s→微信大包
```
此规则在实际数据反推中100%正确：
- 联通FTP上传：149MB/17s → flow>80且dur<21 → FTP上传 ✓
- 联通微信大包：215MB/24s → flow>80且dur≥21 → 微信大包 ✓
- 电信FTP上传：107MB/17s → flow>80且dur<21 → FTP上传 ✓
- 电信微信大包：215MB/26s → flow>80且dur≥21 → 微信大包 ✓

## 四、总结：3种上行业务的唯一性规则树

```
ul流量段(上行MAC > 5Mbps且持续)
├── flow < 20MB → 微信小包上传 (5MB固定文件, 1~2s完成)
├── 20 ≤ flow < 80 → 未定义(无此范围的标注业务)
├── 80 ≤ flow < 190 → FTP上传(泰尔网测上传)
│   └── 联通149MB/17s, 电信107MB/17s
└── flow ≥ 190 → 微信大包上传 (215MB固定文件, ~24s平均)
```

**跨运营商一致性验证通过**：联通和电信的规律完全一致。

**MMF文件对比验证**：在MMF中查找对应文件名和CRNTI，确认上述标注的时间段确实对应上行流量突发段。MMF中同一CRNTI的PCell行流量与ALL_FTP_DETAIL一致。

**潜在风险**：当上行速率极高（158Mbps）时，大包可能10秒完成215MB，此时flow=215>80且dur=10<21。此时规则会误判为FTP上传。不过实际数据中FTP上传的流量为107~149MB，远低于215MB，所以**flow判断优先于时长判断**可解决此问题。建议在flow≥190时直接判为微信大包，不再用时长相较。当前脚本(flow>80后判断dur)在极小概率(11行/737行≈1.5%)下可能误判。
